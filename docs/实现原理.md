# 实现原理

这份文档解释**它是怎么做到的** —— 数据从哪来、经过了什么处理、为什么这么设计、
哪些地方踩过坑。看懂它，你就能自己改、自己加来源、自己判断产物可不可信。

---

## 一、一句话概括

每天早上无人值守地跑一遍：**拉 15 个上游源（外加 731 个 per-App 文件和 83 个脚本）
→ 体检 → 去重修正 → 合成三层产物 → 自检 → 发布到 `release` 分支**。
全程 2 分钟（上游没变时几乎全是 304 空响应）。

```
 15 个上游 URL + 731 个 per-App 文件 + 83 个脚本
   |
   |  ① fetch    带 ETag 条件请求；上游没变就 304 复用本地缓存；失败回退旧缓存
   v
 cache/raw/                                    上游原始文件（不入库）
   |
   |  ② parse    三种格式 -> 统一中间表示 IR
   v
 Layer{exact, suffix, rules}                   每个域名带着"来自哪些来源"
   |
   |  ③ merge    并集 / 按语义去重 / 策略冲突消解 / 脏数据剔除
   v
 Merged
   |
   |  ④ allowlist + compress   同一份放行名单；父域压缩并把来源归属上交给父域
   v
   |
   |  ⑤ emit
   +----------------> dist/ruleset/*.list       域名表 + 规则集（DOMAIN-SET / RULE-SET）
   +----------------> dist/module/*.srmodule    总模块 / HTTPDNS / 排除解密 / 726 个 per-App
   +----------------> dist/conf/base.conf       代理分组 + 分流 + 引用上面两层
   |
   |  ⑥ verify   7 项自检；有阻断性问题就不发布
   v
 release 分支（单个 orphan 提交强推，避免 28 万行文件每天累积撑爆历史）
```

## 二、为什么要中间表示（IR）

上游的格式有三种，输出也要三种。**不做格式间直接互转**，而是都先转成统一的 IR：

| 输入格式 | 谁在用 | 长什么样 |
| :-- | :-- | :-- |
| `domain_set` | blackmatrix7 | 纯域名表：`foo.com` = 精确，`.foo.com` = 含子域 |
| `ruleset` | 可莉 / iab0x00 / LOWERTOP | `DOMAIN-SUFFIX, ad.com`（有类型、**无策略列**） |
| `surge_conf_rules` | Johnshall | `DOMAIN-SUFFIX,ad.com,Reject`（有类型、有策略） |

IR 长这样：

```python
Rule(kind, value, options, target, source)          # 一条非域名类规则
Layer(exact: {域名: {来源}}, suffix: {域名: {来源}}, rules: [...])
```

**关键设计：每个域名记录它来自哪些来源。** 这一个信息支撑了三件事：

1. **精简版判定** —— "被 2 个以上独立来源都认定"的域名才算高置信，这只靠计数实现
2. **误杀排查** —— 回答"这条规则哪来的、能不能删"
3. **压缩后归属上交** —— 见下面第 1 个算法，不交归属就会漏判

## 三、五个不显然的地方

### 1. 父域压缩：删冗余，但必须把"来源归属"上交给父域

`DOMAIN-SUFFIX` 的语义**包含 apex 自身**：`.foo.com` 已经覆盖 `foo.com` 及其所有子域。
所以只要某个上层后缀在列，它的子域条目（无论精确还是后缀）都是冗余的，可以安全删除。

两个坑：

**坑 A：删了子域，就丢了它的来源归属。**
A 来源写了 `.sub.ad.com`、B 来源写了 `.ad.com`。压缩掉前者之后，
`ad.com` 只剩 B 一个来源，精简版就会漏掉这个域名 —— 但事实上**两个来源都认为这里有广告**。
所以删之前要把归属 union 给父域。

**坑 B：必须归属于"最高"的幸存父域，不能就近取。**
`x.jifen.2345.com` 的中间父域 `jifen.2345.com` 自己也会被 `2345.com` 覆盖而删除，
如果归属交给它，回填时那个键已经不存在了（直接 `KeyError` —— 这是实际踩过的 bug）。
最高的父后缀没有任何上层覆盖者，它必然存活到最后。

### 2. 语义去重：不能只比字符串

同一个规则在可莉的 Surge 版和 SR 版里写法不同：

| 段落 | Surge 版多写了什么 |
| :-- | :-- |
| `[Map Local]` | `status-code=200`（200 本来就是 Map Local 的默认状态码） |
| `[Script]` | 给含逗号的 pattern 加了引号（SR 版不加） |

如果直接按字符串比对并集，**796 条 Map Local 会被当成"新规则"重复导入，产物虚胖一倍**。
所以按段落定义了语义归一规则 `semantic_key()`（`src/module.py`）：

```python
_SEMANTIC_STRIPS = {
    "[Map Local]": (r"\s*status-code\s*=\s*200\b", ""),
    "[Script]":    (r'(pattern\s*=\s*)"([^"]*)"', r"\1\2"),
}
```

效果：4,700 条被正确识别为"语义重复，不导入"，只有 **18 条是真正缺的**（CSDN、财新那批）。

### 3. MITM 主机名反推：让死规则活过来

**问题**：模块里的重写规则要"改某个 host 的响应"，但 `[MITM]` 里没声明要解密它
→ 那个 HTTPS 请求根本不会被解密 → **规则永远不会执行，而且没有任何报错**。

排查东方财富失效时发现的：它的 per-App 模块里混进了"东方航空"的规则，
`[MITM]` 写的是 `app.ceair.com` 而不是东方财富的域名。扩大排查后确认这是**系统性问题**：
726 个 per-App 模块里 **50 个中招，共 69 条死规则**，其中 14 个模块的 MITM 列表干脆是空的
（得物、国航、彩云天气、IT之家、横店影视、小米商城、腾讯新闻…）。

**做法**：从规则的匹配模式里**反推主机名**（`src/module.py: derive_mitm_hosts`）。
细节：

- 必须处理正则转义：`emdcadvertise\.eastmoney\.com` → `emdcadvertise.eastmoney.com`
- 上游还会用 `?` 和 `*` 当通配（`api*.futunn.com`、`api-access.pangolin-sdk-toutiao?.com`），
  比对时要展开
- **金融守卫**：命中关键词（`bank`/`futunn`/`eastmoney`/`abchina`/`creditcard`…）的域名
  **不自动开解密**，只写进报告。理由：银行/券商/支付类普遍有证书固定与风控，
  多解密一个这类域名就可能让用户登录不了或交易失败 —— **这个风险不该由构建脚本替用户承担**。
  用户确认没问题后可以自己写进 `config/mitm-extra.txt`。

结果：自动补上 **64 个**主机名（总模块 MITM 946 → 1,010），拦下 **7 个**金融类。

### 4. 放行名单必须同时作用于三层

小火箭里 **模块的规则优先级高于配置文件**。
所以"把域名从域名层的名单里删掉"是**不够的** —— 模块里那 2,800 条 `REJECT` 照样会拦，
这就是"加了白名单还是打不开"的原因。

同一份 `config/allowlist.txt` 同时作用于：

| 层 | 作用方式 |
| :-- | :-- |
| 域名层 | 从合并结果里剔除该域名 |
| 模块层 | 从模块的 `[Rule]` 段里剔除对应的拦截规则 |
| 配置层 | 在 `base.conf` 的 `[Rule]` **最前面**生成一条 `DIRECT` 规则（优先级最高） |

放行名单的语法有意做成两种，因为语义确实不同：
`foo.com` = 放行 foo.com 及所有子域；`*.foo.com` = 只放行子域，apex 仍拦。

### 5. 拉取：ETag 条件请求（每日流水线的关键）

无人值守的每日构建有个两难：**每天重下 30MB**，还是**缓存住就永远拿不到更新**？

做法是把 ETag 存进清单，下次带上 `If-None-Match`：

- 上游没变 → 返回 304 → 复用本地文件，几乎零流量
- 上游变了 → 返回 200 → 下载并更新清单
- 下载失败但有旧缓存 → **回退旧缓存**（构建不中断，但报告里标出来）

per-App 的 731 个文件更省：用 GitHub 的 git trees API 拿每个文件的 blob sha，
**只下载 sha 变了的**（而且这 1 次 API 请求还要用 token，因为匿名限额 60 次/小时
而 Actions 的出口 IP 是共享的）。

> 这里踩过一个坑：缓存键一开始用了 Python 内置 `hash()`。
> 它对字符串的哈希**每个进程都随机化**（PYTHONHASHSEED），
> 导致每次构建缓存键都不同、清单永远命中不了。改用 sha1 派生稳定 id。

## 三之二、脚本指纹门禁：为什么上游改脚本不会静默生效

模块层 231 条规则会执行 83+ 个第三方 JS 脚本，它们**能读到被解密请求的内容**。
而这些脚本是**跟随上游自动更新**的 —— 上游被投毒（或账号被盗后）的话，
恶意代码会静默进入产物。规则错了顶多误拦，脚本被投毒是数据泄露级别的风险。

所以加了一道和"自动更新"配套的门禁（`src/pins.py`）：

| 情况 | 行为 |
| :-- | :-- |
| 内容与指纹一致 | 正常发布 |
| **出现新脚本 / 内容变化** | **停止发布**（用户手上继续是上一版），生成变更报告 |
| 人工确认后 | 更新 `config/script-pins.txt` 并提交 → 恢复发布 |

变更报告会给每个改动脚本列出**值得看一眼的行**（`$httpClient` / `fetch(` /
`eval(` / `atob(` 这类），把"读 83 个脚本的 diff"缩小到"读几行可疑代码"。

人工确认有两条路：本地 `python src/build.py --update-script-pins`，
或在 GitHub 上 Actions → build → Run workflow → 勾选 `accept_scripts`（会提交更新后的指纹）。

**设计取舍**：没有做成"完全自动跟随"（不安全），也没有做成"每个脚本都手动锁定"
（维护不动）。而是"自动跟随 + 内容变化必须被人看过一次"。

## 四、自检门禁：为什么产物可信

每次构建结束都会跑一遍（`src/verify.py`），报告写在 `build-report-verify.md`：

| 检查 | 为什么需要 |
| :-- | :-- |
| 段落名合法性 | 小火箭不认的段落（`[Panel]` 等）一旦漏进产物会解析异常 |
| 规则类型合法性 | 出现小火箭不支持的规则类型说明这条规则会被静默忽略 |
| 域名表语法 | 脏数据（如单标签的 `.pagespeed-mod`）会被当成顶级域后缀 |
| 脚本本地化完整性 | 所有 `script-path` 必须指向本仓库且文件真实存在 |
| 配置引用有效性 | `base.conf` 引用的产物必须都真的产出了 |
| **隐私检查** | 产物里不能出现节点定义、密码、订阅令牌 —— 公开仓库的底线 |
| **规则数突变** | 相比上次构建跌超 20% 直接判失败 —— 上游挂掉的典型征兆 |

**过不了关会怎样**：workflow 直接把构建标成失败，**不发布 `release` 分支** ——
用户手上的还是上一版好的规则，而不是一份被上游故障污染的空壳。

## 六、代码地图

| 文件 | 职责 | 关键点 |
| :-- | :-- | :-- |
| `src/util.py` | 下载、缓存、编码、域名规整 | ETag 条件请求；多编码回退（上游 utf-8/gbk/bom 混杂） |
| `src/parse.py` | 三种输入格式 → IR | 复合规则（AND/OR）单独计数；策略名大小写归一 |
| `src/merge.py` | 合并 / 去重 / 压缩 / 放行 | 父域压缩的归属上交（含"最高父域"那个坑） |
| `src/module.py` | 模块解析与修正 | 语义去重、脏数据校验、参数声明解析、MITM 反推 + 金融守卫 |
| `src/vendor.py` | 脚本本地化与体检 | 路径映射保留出处；静态扫描小火箭不支持的 API |
| `src/apps.py` | per-App 模块生成 | 用 blob sha 判断增量；同名变体归并（修上游 5 组重复 App） |
| `src/emit_*.py` | 三层产物输出 | 产物头部带来源署名与用法；URL 为 release 分支相对路径 |
| `src/verify.py` | 产物自检门禁 | 隐私检查 + 规则数突变检测 |
| `src/lookup.py` | 误杀排查 | 直接给出"该往 allowlist 加哪一行" |

## 七、平台限制：为什么只支持 iOS

**产物只面向 Shadowrocket（小火箭），不支持安卓，也不支持 iPhone 上的其他代理 App。**
这不是懒得做，而是由它的技术路线决定的：

| 产物 | 依赖的小火箭/Surge 语法 | 安卓对应物 |
| :-- | :-- | :-- |
| `conf/base.conf` | `[Proxy Group]` + `policy-regex-filter`、`DOMAIN-SET`、`RULE-SET`、`%APPEND%` | 无（Clash 用 YAML + `rule-providers`） |
| `module/*.srmodule` | `[URL Rewrite]`/`[Header Rewrite]`/`[Body Rewrite]`/`[Map Local]`/`[Script]`/`[MITM]` | 无 |
| `ruleset/*.list` | "有规则类型、无策略列"的规则集写法 | 无（Clash 要 YAML `payload:`） |

**更根本的是能力问题，不是格式问题。** 本项目最核心的价值（模块层：去开屏广告、
改响应体）建立在 **HTTPS 解密（MITM）+ JS 脚本**之上，而：

- **Clash / Mihomo 没有 MITM** —— 不解密就没法改写响应内容
- **sing-box 不支持脚本**
- v2rayNG 等只做分流

所以就算把域名层转成 Clash YAML，安卓用户拿到的也只是
"① 域名层"那一部分 —— 能拦掉大部分广告，但**一点开屏广告都去不掉**。

**为什么不做安卓支持**：技术上可以新增一层输出（把域名层的域名转成 Clash YAML /
sing-box JSON / AdGuard 的 `||domain^`），域名本身是通用的、转格式也不难。
**但本项目决定不做**，因为它只能覆盖①域名层，而**安卓客户端从原理上就拿不到
本项目的核心价值** —— Clash 没有 MITM、sing-box 没有脚本，去开屏广告无从谈起。
让域名层再换一个格式、再多维护一套产物，收益远小于成本。

安卓用户请直接去上游取现成格式（blackmatrix7 的 `rule/Clash/`、`rule/AdGuard/`）——
那是同一批数据源，而且维护得比转换更好。

## 八、这套设计换来了什么

| 指标 | 数值 |
| :-- | :-- |
| 域名层 | 285,799 条（精确 16,274 + 含子域 269,526），合并 5 个来源 |
| 父域压缩去掉冗余 | 1,343 条 |
| 上游重复规则 | 删除 167 条（上游合并脚本的 bug 产物） |
| Surge 版补齐 SR 版缺失 | 18 条（另 4,700 条为语义重复，未重复导入） |
| 模块层 | 4,504 条 + 726 个 per-App 模块 + 83 个本地化脚本 |
| MITM 主机名 | 1,010 个（补上 64 个原本失效的，拦下 7 个金融类） |
| 精简版（≥2 个来源） | 60,148 条 |
| 单次全量构建 | 约 2 分钟（上游无变化时更短） |

**一句话**：这个项目的价值不在"又收集了一份规则"，而在于**它知道自己哪里可能出错，
并且在每次构建时都检查一遍**。
